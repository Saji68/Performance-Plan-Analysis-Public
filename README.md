# داشبورد تجربه همکاری

داشبورد تحلیل ارزیابی ۳۶۰ درجه: فایل ذی‌نفعان (اکسل) و گزارش نظرها (HTML از Jira) را می‌گیرد و
نظر هر مدیر و ذی‌نفع دربارهٔ هر همکار، ارزیابی‌های ثبت‌نشده، و الگوهای نمره‌دهی مشکوک را نشان می‌دهد.

**همهٔ پردازش داخل مرورگر انجام می‌شود.** هیچ فایلی به هیچ سروری ارسال نمی‌شود؛ حتی وقتی صفحه روی
GitHub Pages میزبانی شده باشد، فایل‌های شما از کامپیوترتان خارج نمی‌شوند.

---

## فایل‌ها

| فایل | نقش |
|---|---|
| `index.html` | صفحهٔ اصلی (ساختار + استایل) |
| `core.js` | هستهٔ محاسباتی: تطبیق نام‌ها، تبدیل پاسخ به نمره، تگ‌گذاری، تحلیل توزیع |
| `app.js` | لایهٔ نمایش: جدول‌ها، نمودارها، خروجی اکسل |
| `assets/mark.png` | نشان کارگزاری مفید |
| `vendor/xlsx.full.min.js` | کتابخانهٔ SheetJS برای خواندن اکسل (محلی، تا آفلاین هم کار کند) |
| `data.json` | **اختیاری** — دادهٔ مشترک؛ اگر کنار `index.html` باشد، هر بازدیدکننده بدون بارگذاری فایل آن را می‌بیند |
| `dashboard-single.html` | همان داشبورد در **یک فایل مستقل** — برای ایمیل‌کردن یا اجرای آفلاین |
| `.nojekyll` | به GitHub می‌گوید فایل‌ها را دست‌نخورده منتشر کند |

## اجرای محلی (بدون GitHub)

ساده‌ترین راه: روی `dashboard-single.html` دوبار کلیک کنید تا در مرورگر باز شود. تمام.

اگر می‌خواهید نسخهٔ چندفایلی را اجرا کنید، `index.html` را هم می‌توانید مستقیم باز کنید؛
و اگر مرورگرتان به فایل‌های کناری اجازهٔ اجرا نداد، در پوشه یک سرور محلی بالا بیاورید:

```bash
python -m http.server 8000
# سپس در مرورگر: http://localhost:8000
```

> برای خواندن فایل اکسل، کتابخانهٔ SheetJS از CDN بارگذاری می‌شود؛ پس بار اول باید اینترنت وصل باشد.

## انتشار روی GitHub Pages (رایگان)

### گام ۱ — حساب و مخزن

1. اگر حساب GitHub ندارید، در <https://github.com/signup> بسازید.
2. روی **+** بالا سمت راست → **New repository**.
3. نام مخزن: `mofid-hamkari` (یا هر نام دیگری). گزینهٔ **Public** را بزنید.
   *(روی مخزن Private هم Pages کار می‌کند، اما فقط در پلن‌های پولی GitHub.)*
4. **Create repository**.

### گام ۲ — بارگذاری فایل‌ها

در صفحهٔ مخزن: **Add file** → **Upload files** → کل محتویات این پوشه را بکشید و رها کنید
(`index.html`، `core.js`، `app.js`، پوشهٔ `assets` و `.nojekyll`) → پایین صفحه **Commit changes**.

> اگر `.nojekyll` در فهرست فایل‌ها دیده نمی‌شود، چون با نقطه شروع می‌شود پنهان است؛
> در مک با `Cmd+Shift+.` و در ویندوز از View → Hidden items نمایش دهید.

### گام ۳ — روشن‌کردن Pages

**Settings** (بالای مخزن) → از ستون کنار، **Pages** →
در بخش *Build and deployment*:

- **Source**: `Deploy from a branch`
- **Branch**: `main` و پوشهٔ `/ (root)`
- **Save**

### گام ۴ — آدرس داشبورد

یکی دو دقیقه بعد، در همان صفحهٔ Pages آدرس ظاهر می‌شود:

```
https://<نام-کاربری>.github.io/mofid-hamkari/
```

نکته: اگر نام مخزن را دقیقاً `<نام-کاربری>.github.io` بگذارید، آدرس کوتاه‌تر می‌شود:
`https://<نام-کاربری>.github.io/`

### گام ۵ — به‌روزرسانی بعدی

برای تغییر داشبورد، همان فایل را دوباره Upload کنید (GitHub می‌پرسد جایگزین شود یا نه) یا
مستقیم در خود GitHub روی فایل → آیکن مداد → ویرایش → Commit. تغییرات ظرف یکی دو دقیقه روی سایت می‌آید.

## استفاده

1. **فایل ذی‌نفعان (اکسل)** را بارگذاری کنید — ستون‌ها به ترتیب: نام همکار، مدیر مستقیم، ذی‌نفع ۱، ذی‌نفع ۲، ذی‌نفع ۳.
2. **گزارش نظرها** را بارگذاری کنید — در Jira فیلتر «تجربه همکاری» را باز کنید و
   *Export → HTML (current fields)* بگیرید.
3. سال ارزیابی را از نوار فیلتر انتخاب کنید (پیش‌فرض: جدیدترین سال).
4. روی هر سطر کلیک کنید تا همهٔ نظرها و دلیل تگ‌خوردن آن فرد را ببینید.
5. تب **توزیع نمرهٔ نهایی** را ببینید تا تصویر کلی سازمان و هشدارهای آماری را بگیرید.
6. در ستون «وضعیت نمرهٔ نهایی» تکلیف هر نفر را مشخص کنید.
7. **خروجی اکسل** فهرست نمرات نهایی افراد را می‌دهد.

داده‌های بارگذاری‌شده در همان مرورگر ذخیره می‌شوند، پس دفعهٔ بعد داشبورد با همان داده باز می‌شود.
دکمهٔ **پاک کردن داده‌ها** آن‌ها را حذف می‌کند.

## دادهٔ مشترک — تا بقیه بدون بارگذاری فایل ببینند

`localStorage` مخصوص یک مرورگر روی یک دستگاه است؛ بنابراین به‌تنهایی داده را با کسی به اشتراک
نمی‌گذارد. برای اینکه همه یک داده ببینند، یک فایل `data.json` کنار سایت می‌گذارید:

1. یک نفر (شما) هر دو فایل را در داشبورد بارگذاری می‌کند و در صورت نیاز تصمیم‌های
   «وضعیت نمرهٔ نهایی» را هم ثبت می‌کند.
2. دکمهٔ **ذخیره برای همه** را می‌زند → فایل `data.json` دانلود می‌شود.
3. همان `data.json` را کنار `index.html` در سایت آپلود می‌کند.
4. از این به بعد هر کس لینک را باز کند، داشبورد خودش `data.json` را می‌خواند و همان داده،
   همان تحلیل و همان تصمیم‌ها را می‌بیند — بدون هیچ بارگذاری.

بالای صفحه نوشته می‌شود «دادهٔ مشترک سایت — آخرین ذخیره: …» تا معلوم باشد داده از کِی است.
برای هر دور جدید ارزیابی، همین چهار گام تکرار می‌شود.

**تصمیم‌های کالیبراسیون:** `data.json` تصمیم‌های ثبت‌شده را هم با خودش می‌برد و مبنای مشترک
می‌شود. هر بازدیدکننده می‌تواند روی همان مبنا تصمیم‌های خودش را هم ثبت کند؛ آن‌ها در مرورگر
خودش می‌ماند تا وقتی `data.json` تازه‌ای بیاید. اگر می‌خواهید تصمیم‌های جلسه برای همه ثبت شود،
بعد از جلسه دوباره **ذخیره برای همه** بزنید و `data.json` را جایگزین کنید.

> ⚠️ **نکتهٔ مهم دربارهٔ حریم خصوصی:** با این روش دادهٔ ارزیابی کارکنان (نام‌ها، نمره‌ها و
> متن نظرها) کنار سایت می‌نشیند و هر کسی که به آدرس سایت دسترسی دارد می‌تواند
> `آدرس-سایت/data.json` را باز کند. بنابراین **این حالت را روی GitHub Pages عمومی نگذارید.**
> یکی از این دو را انتخاب کنید:

### میزبانی خصوصی با Cloudflare Pages (رایگان، روی مخزن private)

1. مخزن GitHub را **Private** بسازید و فایل‌ها را در آن بگذارید.
2. در <https://dash.cloudflare.com> → **Workers & Pages** → **Create** → **Pages** →
   **Connect to Git** → مخزن را انتخاب کنید.
3. Framework preset را روی `None` بگذارید، Build command را خالی بگذارید و
   Build output directory را `/` بگذارید → **Save and Deploy**.
4. در **Settings → Access policy** (یا Cloudflare Zero Trust → Access) دسترسی را به
   ایمیل‌های سازمانی محدود کنید؛ آن‌وقت فقط همکاران مجاز می‌توانند داشبورد را باز کنند.

### یا: بدون هیچ میزبانی

`data.json` را نگذارید و به‌جایش فایل `dashboard-single.html` را به‌همراه همان دو فایل ورودی
در اسلک/ایمیل بفرستید؛ هر کس خودش بارگذاری می‌کند. داده روی هیچ سروری قرار نمی‌گیرد.

## منطق تگ‌ها

همهٔ آستانه‌ها بر حسب **درصد** هستند و نسبت به **میانگین واقعی سازمان** تنظیم می‌شوند، نه وسط مقیاس.

| تگ | شرط |
|---|---|
| نمرهٔ بالای مشکوک | دست‌کم ۲ نظر، نمرهٔ نهایی ≥ ۸۵٪ و کمینهٔ نمره ≥ ۷۵٪ — یعنی همه یکی از دو گزینهٔ بالای فرم خود را داده‌اند |
| نمرهٔ پایین مشکوک | دست‌کم ۲ نظر و بالاترین نمرهٔ دریافتی ≤ ۵۰٪ — یعنی همه یکی از دو گزینهٔ پایین فرم خود را داده‌اند |
| اختلاف نظر | دامنه ≥ ۵۰ واحد درصد، یا فاصلهٔ مدیر با میانگین ذی‌نفعان ≥ ۳۰ واحد، یا پراکندگی ذی‌نفعان ≥ ۵۰ واحد |
| تناقض متن و نمره | نمرهٔ ≥۷۵٪ با توضیح منفی، یا نمرهٔ ≤۴۰٪ با توضیح مثبت |
| طبیعی | دست‌کم ۲ نظر و هیچ‌کدام از شرایط بالا |
| داده ناکافی / بدون نظر | کمتر از ۲ نظر |

برای تغییر آستانه‌ها، مقادیر `DEFAULTS` را در `core.js` ویرایش کنید.

## ستون توضیحات

اگر در خروجی Jira ستون متنی (توضیحات / شرح / بازخورد) هم باشد، داشبورد خودش آن را از سربرگ جدول
پیدا می‌کند — چه با نام گویا و چه از روی طول متنِ ستون‌های ناشناخته. ستون‌های شناسایی‌شده در تب
**راهنما** فهرست می‌شوند تا تشخیص را تأیید کنید.

بار هر متن (مثبت / منفی / دوسویه / خنثی) با فهرست واژگان فارسیِ بازخورد کاری در `core.js` سنجیده
می‌شود: اول عبارت‌های چندکلمه‌ای («نیاز به بهبود»، «به موقع») تطبیق داده و از متن حذف می‌شوند، بعد
واژه‌های تکی با در نظر گرفتن نفی («دقیق نبود») شمرده می‌شوند. با نگه‌داشتن نشانگر روی برچسبِ بار متن،
واژه‌هایی که شمرده شده‌اند دیده می‌شوند.

> این سنجش واژگانی است، نه درک معنا؛ طعنه و جملهٔ پیچیده را اشتباه می‌فهمد. برچسب‌ها را نقطهٔ شروع
> بررسی انسانی بگیرید. واژگان در `NEG_PHRASES` / `POS_PHRASES` / `NEG_WORDS` / `POS_WORDS` قابل ویرایش است.

## نمرهٔ نهایی

### اول: هر پاسخ به درصد تبدیل می‌شود

سه فرم ارزیابی، سه مقیاس با **طول متفاوت** دارند، پس گزینه‌ها را نمی‌توان مستقیم با هم جمع کرد.
درصد هر گزینه طبق جدول ابلاغی سازمان تعیین شده است:

**مدیر مستقیم**

| ٪ | گزینه |
|---|---|
| ۲۰ | عملکرد ضعیف |
| ۴۰ | نیاز به ارتقا در انجام کار محوله |
| ۶۰ | کار محوله را به صورت مطلوب انجام داده است |
| ۸۰ | کار محوله را نه تنها مطلوب انجام داده بلکه به اهداف برنامه عملکرد نیز دست یافته است |
| ۱۰۰ | فراتر از انتظارات عملکرد |

**ذی‌نفعان**

| ٪ | گزینه |
|---|---|
| ۲۵ | انتظارات برآورده نشده است |
| ۵۰ | انتظارات تا حد خوبی انجام شده است |
| ۷۵ | انتظارات را کامل و مطلوب انجام داده است |
| ۱۰۰ | بیش از انتظارات عمل کرده است |

**خودارزیابی (سلف ریفلکشن)**

| ٪ | گزینه |
|---|---|
| ۰ | عملکرد ضعیف در انجام مسئولیت‌ها مطابق برنامه عملکرد |
| ۲۰ | نیاز زیاد به اصلاح عملکرد در انجام مسئولیت‌ها مطابق برنامه عملکرد |
| ۴۰ | عملکرد متوسط در انجام مسئولیت‌ها مطابق برنامه عملکرد |
| ۶۰ | عملکرد مطلوب در انجام مسئولیت‌ها مطابق برنامه عملکرد |
| ۸۰ | علاوه بر عملکرد مطلوب، رسیدن به تمامی اهداف برنامه عملکرد |
| ۱۰۰ | عملکرد فراتر از اهداف و مسئولیت‌ها مطابق برنامه عملکرد |

هر گزینه چند «کلید متنی» دارد تا هم عبارت نسخهٔ فعلی فرم و هم عبارت نسخه‌های قبلی (که در
گزارش‌های قدیمی‌تر Jira هست) شناسایی شود — مثلاً «فراتر از انتظارات عملکرد» و «فراتر از
برنامه عملکرد» هر دو ۱۰۰٪ می‌گیرند.

> گزینهٔ «ستارهٔ مدیریت دارایی» فرم مدیران را کمیته می‌دهد نه مدیر مستقیم، و اصلاً وارد
> محاسبه نمی‌شود. اگر در گزارش دیده شود، در تب راهنما زیر «پاسخ‌های کنارگذاشته‌شده» فهرست می‌شود.

مقیاس هر پاسخ از **فرمی** گرفته می‌شود که واقعاً پر شده (پیشوند «مدیران - » یا «ذی‌نفعان - » در
خروجی Jira)، نه از جایگاه آن فرد در فایل اکسل. اگر مدیرِ کسی فرم ذی‌نفعان را پر کرده باشد، نمره‌اش
روی مقیاس ذی‌نفع حساب می‌شود ولی وزن ۰.۶ مدیر را می‌گیرد.

### بعد: ترکیب وزنی

درصد سه ذی‌نفع با هم میانگین گرفته می‌شود و بعد با وزن **۰.۴** در کنار درصد مدیر مستقیم با وزن **۰.۶**
ترکیب می‌شود:

```
نمرهٔ نهایی (٪) = (درصد مدیر × ۰.۶) + (میانگین درصد ذی‌نفعان × ۰.۴)
```

اگر هیچ ذی‌نفعی نظر نداده باشد وزن مدیر ۱ می‌شود، و اگر مدیر نظر نداده باشد وزن ذی‌نفعان ۱ می‌شود.
وزن‌ها در `DEFAULTS` داخل `core.js` (کلیدهای `wMgr` و `wStk`) و درصد و متن گزینه‌های هر مقیاس در
`SCALES` قابل تغییرند.

در ستون **وضعیت نمرهٔ نهایی** جدول تحلیل، برای هر نفر یکی از این حالت‌ها انتخاب می‌شود:

- **تایید شده (توسط مدیر)** — همان نمرهٔ وزنی ثبت می‌شود.
- **تایید شده (در جلسه کالیبراسیون)** — همان نمرهٔ وزنی، با مهر جلسهٔ کالیبراسیون.
- **تغییر کرده (طبق جلسه کالیبراسیون)** — کادر عددی باز می‌شود تا نمرهٔ تأییدشدهٔ جلسه دستی وارد شود.

انتخاب‌ها در مرورگر ذخیره می‌مانند و دکمهٔ **خروجی اکسل** فقط همین نمرات نهایی را بیرون می‌دهد.

## توزیع نمرهٔ نهایی

تب **توزیع نمرهٔ نهایی** همان نمرات را یک‌جا نگاه می‌کند تا معلوم شود سیستم ارزیابی در کل سازمان
چطور رفتار کرده است، نه فقط تک‌تک افراد.

**نمودار.** هر ستون یک بازهٔ ده‌درصدی است (۰ تا ۱۰٪، ۱۰ تا ۲۰٪ و …) و ارتفاعش تعداد افرادِ آن بازه؛
با نگه‌داشتن نشانگر روی ستون نام‌ها دیده می‌شوند. ستون‌های زیر ۵۰٪ قرمز رنگ می‌شوند.
نوار روشنِ پشت نمودار نیمهٔ میانی افراد (چارک اول تا سوم) است، خط تیره میانگین و خط نازک میانه را نشان می‌دهد.
کلید بالای نمودار بین **نمرهٔ محاسبه‌شده** (خروجی فرمول) و **نمرهٔ تأییدشده** (نتیجهٔ جلسهٔ کالیبراسیون) جابه‌جا می‌شود.

**کارت‌های آماری.** تعداد نمره‌شده، میانگین، میانه، انحراف معیار، دامنه، دامنهٔ میان‌چارکی و شکل توزیع.

**باندهای عملکردی.** پنج سطح: برجسته (۹۰٪ و بالاتر)، بالاتر از انتظار (۷۵ تا ۹۰٪)،
مطابق انتظار (۵۰ تا ۷۵٪)، نیازمند بهبود (۳۰ تا ۵۰٪)، نیازمند اقدام (زیر ۳۰٪).

**مبنای محاسبهٔ نمره.** کسانی که فقط مدیرشان یا فقط ذی‌نفعانشان نظر داده‌اند، نمره‌شان با وزن ۱
همان یک طرف ساخته شده و با بقیه هم‌مقیاس نیست؛ تعدادشان اینجا جدا گزارش می‌شود.

**تحلیل خودکار.** جعبه‌های پایین تب، همین اعداد را تفسیر می‌کنند و در این حالت‌ها هشدار می‌دهند:

| وضعیت | شرط | چرا مهم است |
|---|---|---|
| فشردگی نمرات | انحراف معیار ≤ ۱۱ واحد درصد | نمره بین افراد تمایزی ایجاد نمی‌کند |
| پراکندگی زیاد | انحراف معیار ≥ ۲۲ واحد درصد | احتمال نبودِ معیار مشترک بین ارزیاب‌ها |
| تورم نمره | ۶۰٪ یا بیشتر افراد نمرهٔ ۷۵٪ و بالاتر | نمره‌دهی تعارفی؛ رتبه‌بندی نسبی لازم است |
| تمرکز در یک بازه | ۴۰٪ یا بیشتر در یک ستون | تصمیم باید به متن نظرها تکیه کند |
| مبنای ناهمگن | وجود افراد تک‌طرفه | نمرات هم‌مقیاس نیستند |
| اثر کالیبراسیون | جابه‌جایی یک‌طرفهٔ نمرات در جلسه | فرمول با قضاوت مدیران هم‌راستا نیست |

آستانه‌ها در `distribution()` داخل `core.js` قابل تغییرند
(`tightSd`، `wideSd`، `inflateBand`، `inflateShare`) و مرز باندها در آرایهٔ `BANDS`.

## تطبیق نام‌ها

نام‌ها در Jira لاتین («نام‌خانوادگی، نام») و در اکسل فارسی‌اند. `core.js` هر دو را به یک
اسکلت آوایی تبدیل و بهترین انطباق را پیدا می‌کند؛ املاهای مختلف یک نام در اکسل هم یکی در نظر
گرفته می‌شود. اگر نامی اشتباه تطبیق داده شد، در تب **تطبیق نام‌ها** دستی اصلاحش کنید — انتخاب شما ذخیره می‌ماند.
